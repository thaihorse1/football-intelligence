# v0.3C: API-Football fixtures

Initial coverage is Bundesliga (`BL1`, API-Football league `78`). The new
collector uses the direct API-SPORTS endpoint, not the RapidAPI gateway.
Set `API_FOOTBALL_API_KEY` in `.env` for Docker, or export it for local runs.
Local Python commands do not load `.env` automatically.

Provider references:
- https://www.api-football.com/documentation-v3
- https://www.api-football.com/news/post/how-to-get-started-with-api-football-the-complete-beginners-guide

## Collect and reconcile

Build the image after changing source or aliases:

```sh
docker compose build api-football
docker compose run --rm api-football > /tmp/api_football_bl1.json
```

The default window is 30 days. Optional arguments follow the module name:

```sh
docker compose run --rm api-football python -m app.api_football_fixtures --days 7 --season 2026
```

Without `--season`, requests cover each German season overlapping the window,
using July as the season boundary. API plan restrictions or quota errors fail
the command. A successful empty response is a valid empty report. Multiple
response pages fail explicitly instead of producing a partial schedule.

After a successful collection, inspect the temporary report before using it:

```sh
python3 -m json.tool /tmp/api_football_bl1.json
python3 -m app.reconcile_fixtures \
  --football-data data/football_data_bl1.json \
  --openliga data/openliga_fixtures.json \
  --api-football /tmp/api_football_bl1.json
```

Use reports collected over the same window and at comparable times. Omitting
`--api-football` retains the original two-provider behavior and output shape.
Supplying an empty third report still enables three-provider rules.

## Collector contract

Core fixture fields match the existing collectors: provider and fixture ID,
competition, home/away IDs and names, UTC/Bangkok kickoff, and status.
`competition_code` is `BL1`; `verification_status` is `SOURCE_ONLY`.
`provider_status` retains `NS`, normalized to `SCHEDULED`.
Only not-started (`NS`) fixtures are included. TBD, postponed, cancelled,
finished, and in-progress fixtures are excluded. This report describes the
upcoming schedule, not every possible fixture state.

The precise window is start-inclusive and end-exclusive in UTC. Results are
sorted and deduplicated by provider fixture ID. Conflicting duplicates,
malformed scheduled fixtures, HTTP failures, and API error envelopes fail the
entire run with a nonzero exit and no JSON report on stdout. Identical
duplicates are collapsed. Team IDs and fixture IDs remain provider-specific.

## Three-provider rules

The CLI filters all inputs to Bundesliga. Each result retains the original
`football_data`, `openliga`, and `api_football` observations; missing ones are
null. `source_count` and `missing_sources` make coverage explicit. A missing
source is not evidence of cancellation.

Candidate pairs must have kickoff times within 24 hours and either matching
canonical home/away names or an average name similarity of at least 0.78.
All observations in a group must match pairwise, with at most one observation
per provider. A component with competing candidates or a nontransitive match
chain is emitted as separate `AMBIGUOUS_MATCH` records with candidate IDs.
No observation is discarded or arbitrarily selected.

For unambiguous groups, `MATCHED` means canonical names agree and the largest
pairwise kickoff difference is at most 15 minutes. Two sources can be matched
while the third is missing. Fuzzy name agreement yields `TEAM_NAME_CONFLICT`;
a larger time difference yields `KICKOFF_CONFLICT`. The `conflicts` array
retains both disagreements when present. Majority agreement does not hide a
third-source disagreement. Singletons use `ONLY_<SOURCE>`.

Fixtures separated by more than 24 hours remain separate; large reschedules
require manual review. These conservative rules can produce extra ambiguous
records when club names are similar. No preferred provider or canonical
kickoff is selected automatically.

## Validation

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests -v
docker compose --profile collectors config --quiet
git diff --check
```

Tests use synthetic provider payloads and mocked HTTP responses; no credentials
or paid API calls are required. Live API plan access and the accuracy of actual
provider schedules require a separate live report review before committing.
