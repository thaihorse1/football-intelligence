# v0.5A — Evidence Contract & Source Registry

The evidence layer records what was learned about a candidate, which source
reported it, publication and retrieval times, and how it was acquired. It accepts
one candidate ID and a collection of raw observations, validates and normalizes
them, assigns stable hashes and IDs, and produces a deterministic evidence bundle.
Candidate IDs can come from the v0.4B candidate universe or another future format;
no `sfi:` prefix is required. Candidate verification remains unchanged.

Evidence is source-reported information, not established truth. REPORTED means
that the source reported the claim; it does not mean the claim has been verified
as true. The layer preserves “Source says player is doubtful” as a source claim
and does not transform it into “Player is doubtful.” Gathering and synthesis are
separate stages. Contradictions coexist for later synthesis; this layer neither
judges claims nor resolves disagreements. Provenance is mandatory. No numeric
confidence, source ranking, sentiment or betting decision is manufactured.

## Sources and acquisition

The initial `config/evidence_sources.json` contains only Wettbasis, Wettfreunde,
LeagueLane and Gooners Guide, registered as enabled TIPSTER sources. It contains
no unverified domains or URLs and no reliability scores. Official/team/local media
sources will be added as they are onboarded and verified.

Registry entries contain exactly name, source_type and enabled. The registry must
be a nonempty object. IDs consist of lowercase letters and numbers separated by single hyphens;
leading, trailing and consecutive hyphens are rejected; names must be
nonempty and enabled must be a real boolean. Source types are OFFICIAL,
PRIMARY_MEDIA, REPUTABLE_MEDIA, SPECIALIST, TIPSTER and OTHER. Duplicate JSON keys
and unknown registry fields are rejected. Unknown or disabled evidence sources
are fatal validation failures.

Acquisition technology is intentionally abstracted. API, DIRECT_HTTP, SCRAPY,
CRAWL4AI, FIRECRAWL and USER_SUPPLIED are provenance labels only. Firecrawl,
Crawl4AI, Scrapy and direct HTTP acquisition implementations are not introduced
here; they will be evaluated in v0.5B. No network requests, API calls, website
scraping, LLM calls or external clients occur in v0.5A.

## Input and use

```
python3 -m app.evidence \
  --input data/candidate-evidence.json \
  --source-registry config/evidence_sources.json
```

The source-registry flag defaults to that path. The required local input is:

```json
{
  "candidate_id": "sfi:abc123",
  "evidence": [
    {
      "evidence_type": "PLAYER_AVAILABILITY",
      "subject": "Player Name",
      "claim": "Source reports player doubtful for Saturday",
      "source_id": "wettbasis",
      "source_url": "https://example.com/article",
      "title": "Match preview",
      "published_at_utc": "2026-10-04T08:00:00+00:00",
      "retrieved_at_utc": "2026-10-04T09:00:00+00:00",
      "acquisition_method": "USER_SUPPLIED",
      "status": "REPORTED",
      "raw_text": "Relevant source text"
    }
  ]
}
```

The example URL is a syntax placeholder, not a verified source URL. URLs must be
nonempty HTTP or HTTPS URLs with a host; syntax is checked locally and the supplied
URL is preserved without fetching it. Malformed ports, whitespace and controls
are rejected.

Candidate IDs, claims and raw text must be nonempty strings. Subject must be a
nonempty string or explicit null for a match-level claim. Publication time must
be a timezone-aware ISO timestamp or explicit null when unavailable. Retrieval
time must be a timezone-aware ISO timestamp. Valid times are converted to UTC.
Title is optional and may be null; a supplied string must be nonempty. Only
REPORTED status is accepted. Raw observations reject missing required and unknown
fields; the input envelope contains exactly candidate_id and evidence. Empty
evidence collections are valid.

Allowed evidence types are PLAYER_AVAILABILITY, LINEUP_ROTATION,
SCHEDULE_MOTIVATION, TACTICAL, MANAGER_COMMENT, TIPSTER_ANGLE, LOCAL_NEWS and OTHER.
Input objects are not mutated. A fatal validation failure prints one sanitized
error to stderr, exits nonzero, and prints no partial bundle to stdout.

Python callers can use `normalize_record(candidate_id, raw, registry)` for a single
observation or `build_bundle(candidate_id, raw_evidence, source_registry)` for a
collection. Both validate the registry and the required evidence fields.

## Normalization, hashes and identity

Raw text normalization converts CRLF and CR to LF, strips trailing whitespace
from each line, and strips leading/trailing whitespace from the complete text.
Internal spaces and case remain unchanged; no semantic rewriting occurs. The
normalized text is output and its UTF-8 SHA-256 digest becomes content_hash.

Evidence identity contains exactly candidate_id, evidence_type, subject, claim,
source_id, source_url, published_at_utc and content_hash. The identity is serialized
with `json.dumps(identity, sort_keys=True, separators=(",", ":"), ensure_ascii=False)`.
Its UTF-8 SHA-256 digest receives the `ev:` prefix. Title, retrieval time and
acquisition method are excluded from identity. The same published evidence
reacquired through another method therefore retains its ID.

Each normalized record contains evidence_id, candidate_id, evidence_type, subject,
claim, source (id, name, source_type, url), title, published_at_utc,
retrieved_at_utc, acquisition (method), status, normalized raw_text and content_hash.
The source name and type come from the validated registry.

## Deduplication and bundle

Only identical evidence IDs collapse. Different claims from one source,
contradictory claims from different sources, and identical text from different
sources coexist. Duplicate IDs retain the record with the latest retrieval,
including that retrieval's acquisition method and title. If retrieval instants
are equal, the lexicographically greatest canonical normalized-record JSON is
used as a deterministic tie-break. This is a mechanical ordering rule, not a
judgment about source or acquisition quality. Inconsistent identity or text behind
one evidence ID fails as an internal collision.

Bundles contain schema_version `0.5A`, actual generated_at_utc, candidate_id,
total_evidence, summary and evidence. Summary contains alphabetically ordered
by_evidence_type and by_source_type count maps. Evidence sorts by publication
instant (null last), retrieval instant, source ID and evidence ID. The contents
and ordering are independent of input order; generated_at_utc may change between
runs and never participates in identity.

Reason: Adopt established provenance/content-hashing/deterministic record
principles while keeping acquisition technology replaceable and separating
evidence collection from evidence interpretation.


Evidence tests use in-memory observations, synthetic registries and temporary
local files. No network calls occur. Earlier collectors and candidate verification
are neither modified nor invoked by the evidence module.
